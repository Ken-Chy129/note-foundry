# NoteFoundry v0.1 Implementation Plan

## Goal

Deliver the knowledge-management core described in `docs/product-scope.md` and prove it with the deployed Hermes Agent acceptance scenario. Each phase below is an independently testable increment and must leave the repository buildable.

## Delivery principles

- Keep PostgreSQL as the runtime system of record and Markdown as canonical note content.
- Organize backend code by business capability, with explicit interfaces between modules.
- Define REST behavior in OpenAPI before exposing an endpoint.
- Require owner authorization for every management operation; public routes expose only published content in public Knowledge Spaces.
- Add domain and persistence tests before implementing new behavior.
- Do not add Learning Sources, Agent execution, semantic retrieval, or multi-user permissions.

## Phase 1: Platform foundation

### 1.1 Configuration and process roles

Acceptance criteria:

- API and worker load validated configuration from environment variables.
- Invalid or missing required production configuration fails fast without logging secrets.
- API health and readiness checks distinguish process health from PostgreSQL readiness.

Verification:

- `go test ./...`
- Start the API with valid and invalid test configuration.

### 1.2 PostgreSQL migrations and test harness

Acceptance criteria:

- Migrations are embedded in the backend binary and applied explicitly.
- PostgreSQL enables `pg_trgm` and stores migration history.
- Integration tests run against a disposable PostgreSQL database.

Verification:

- Apply migrations to an empty database twice without error.
- Run migration and repository integration tests.

### 1.3 OpenAPI and HTTP conventions

Acceptance criteria:

- REST endpoints use a shared structured error format.
- JSON decoding rejects unknown fields and oversized bodies.
- OpenAPI documents every public and management endpoint as it is introduced.

## Phase 2: Knowledge Owner identity

Acceptance criteria:

- GitHub OAuth callback accepts only the configured immutable GitHub User ID.
- Owner sessions are stored server-side and referenced by secure, HTTP-only, SameSite cookies.
- OAuth state is single-use and expires.
- Management endpoints return `401` without a session and never grant write access to another GitHub account.
- Authentication endpoints are rate-limited.

Verification:

- Unit tests cover state validation, owner matching, expiry, and logout.
- HTTP tests cover cookie flags and unauthorized management access.
- A real configured GitHub login succeeds during deployment acceptance.

## Phase 3: Knowledge organization

### 3.1 Knowledge Spaces

Acceptance criteria:

- The owner can create, list, rename, and change the visibility of flat top-level Knowledge Spaces.
- Space names are non-empty and stable IDs are never derived from names.
- Public readers can list only public spaces that contain published content.

### 3.2 Directories

Acceptance criteria:

- Directories nest only within one Knowledge Space.
- Parent changes cannot create cycles or cross-space trees.
- Deleting a non-empty directory requires an explicit supported operation rather than silent cascading.

### 3.3 Tags

Acceptance criteria:

- Tags are global and flat.
- Rename preserves tag identity.
- Merge moves all note associations to the target tag without duplicates.

## Phase 4: Learning Note lifecycle

### 4.1 Create, read, and autosave

Acceptance criteria:

- Learning Notes have immutable IDs independent of title, slug, space, and directory.
- Markdown is stored canonically in PostgreSQL.
- Autosave uses a version value and returns `409` for stale updates.
- New notes in private spaces have private current content; new notes in public spaces begin as private drafts.

### 4.2 Publish and revisions

Acceptance criteria:

- Publishing copies the current draft into Published Content atomically.
- Editing a published note changes only the draft until the next publish.
- Publish, manual checkpoint, and restore create lightweight Note Revisions.
- Restoring a revision preserves note identity and creates a recoverable checkpoint.

### 4.3 Move and Trash

Acceptance criteria:

- Ordinary moves inherit the target Knowledge Space visibility.
- Moving private content into a public space requires explicit confirmation and publishes in the same transaction.
- Trash has no automatic expiry.
- Restore preserves stable identity; permanent deletion is explicit.

## Phase 5: Relationships and content capabilities

### 5.1 Stable Note Links and Backlinks

Acceptance criteria:

- Markdown Note Links target immutable note IDs.
- Saving content derives forward links transactionally.
- Backlinks are queried from forward links and are not separately mutable.
- Anonymous readers see relationships only when both notes are publicly published.

### 5.2 Attachments

Acceptance criteria:

- Attachments use immutable storage keys and recorded media type, size, and checksum.
- Upload limits and allowed media types are validated using content, not only extensions.
- Attachment access inherits owning note visibility and draft/public state.
- Public URLs cannot expose private or unpublished attachment bytes.

### 5.3 Search

Acceptance criteria:

- Weighted `tsvector` search covers title, tags, headings, and body.
- `pg_trgm` provides Chinese substring and similarity fallback.
- Owner search includes authorized private and draft content.
- Anonymous search includes only Published Content in public Knowledge Spaces.
- Search projections can be rebuilt from canonical data.

## Phase 6: Next.js web application

Acceptance criteria:

- Desktop management UI supports sign-in, space/directory organization, note editing, preview, tags, links, revisions, publish, search, and Trash.
- Markdown preview supports code blocks, Mermaid, formulas, tables, images, and stable Note Links.
- Public navigation and search require no account and never reveal drafts or private metadata.
- Public reading is comfortable on mobile; editing is comfortable on desktop.
- Forms expose validation, save, conflict, publish, and failure states clearly.

Verification:

- Type checking, linting, unit/component tests, and production build pass.
- Browser tests exercise the critical owner and anonymous reader paths.

## Phase 7: Durable Jobs and encrypted backups

Acceptance criteria:

- PostgreSQL-backed Jobs support claiming, retries, failure recording, and process restart recovery.
- Scheduled backup Jobs create a consistent PostgreSQL dump plus attachment archive.
- Backup artifacts are encrypted before upload to S3-compatible storage.
- Daily and weekly retention is enforced without deleting the only recoverable backup.
- A documented restore command verifies integrity, restores PostgreSQL and attachments, and refuses unsafe in-place overwrite without explicit confirmation.

Verification:

- Job retry and stale-claim integration tests pass.
- Backup encryption/decryption round-trip test passes.
- A real uploaded backup is restored into a clean deployed instance.

## Phase 8: Deployment and acceptance

Acceptance criteria:

- Docker Compose runs Caddy, Next.js, Go API, Go worker, and PostgreSQL with persistent volumes.
- Caddy routes public web, API, and protected attachments and applies HTTPS/security headers.
- Deployment documentation includes required environment variables, migration, backup, restore, and upgrade procedures.
- The complete Hermes Agent scenario in `docs/product-scope.md` is recorded as passed on the deployed instance.

## External acceptance inputs

Implementation and local verification can proceed without production credentials. Final deployed acceptance requires:

- A GitHub OAuth application and configured owner GitHub User ID.
- A public domain pointing to the deployment host.
- An S3-compatible bucket independent of the application server, with credentials scoped to the backup prefix.
